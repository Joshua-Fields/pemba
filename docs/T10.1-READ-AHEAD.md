# T10.1 design note: fewer Postgres read round trips

Status: chosen in OQ-065; measurements are in `benches/RESULTS.md`.

## Where the round trips go

Derived from `Engine::check` and `Evaluator` at PR #98's merge commit. Each line matches the
baseline in `benches/RESULTS.md`.

- Every request costs 4: `BEGIN`, head and horizon, schema version, `ROLLBACK`.
- Every store read costs 1. `document#view` can make 7 (`viewer`, `editor` and `owner` each
  an exact probe and a subject-set read, plus the `parent` arrow). `folder#view` makes 3.
  `group#member` makes 2.
- `folders_depth_d` is `4 + 7 + 3(d-1) + 1 = 3d + 9`. `groups_depth_d` is `4 + 2d + 1`.
  `lookup_resources_10k` is `4 + 2 + 500`: two reverse seeds, then 500 candidates at one
  exact probe each.

## Options

**(a) One statement per frontier per relation.** Replace per-object reads with a batch over
the objects at a level. This needs a frontier, and the evaluator has none: it is depth-first
and short-circuits, and that order is part of its contract (`05` §2: order decides which
error a check reports). Taken literally as an evaluator rewrite it changes reads and errors.
Taken as a hint it is option (a'). It also misses the headline scenario: a chain's frontier
has width 1, so grouping by relation still leaves `viewer` and `parent` as two statements per
folder (67 round trips at depth 30), and grouping by read kind leaves all 99.

**(a') Read-ahead (chosen).** Keep the evaluator. Add a per-request cache of store answers in
front of its reads. Hints queue reads without I/O: at a node's entry, every read its
expression may make on that object; after an arrow or subject-set read, the same for its
children; in `lookup_resources` phase 2, for a window of candidates. When the evaluator asks
for a read that is not cached, one statement carries it plus the queued hints. Hints are
never evaluated, only fetched.

**(b) Recursive CTE.** As an evaluator, it is a second implementation of `04`. It cannot
express exclusion, intersection or `.all` monotonically, reports no `StaleRelationship`,
wildcard ambiguity or `NonMonotonicCycle`, loses deterministic error order, and has no trace.
Rejected. As a prefetch for the cache in (a') it would be sound and take chains to a constant,
but it needs the schema's edges passed to SQL and has poor planner estimates (compare OQ-054),
and it does not help `lookup_resources`. Not now; (a') leaves it open without touching the
evaluator.

**(c) Open the snapshot in one message (chosen).** Send `BEGIN ...; SELECT head, horizon,
schema version` as one simple query. It uses the same transaction and takes its snapshot at
the same statement. The schema version is then held by the snapshot. Saves 2 per request, on
every read path.

## What each option preserves

| | (a') read-ahead | (b) CTE as evaluator | (c) snapshot message |
|---|---|---|---|
| One snapshot and revision | Every batch runs on the snapshot's connection, with the same range check and `Form` as single reads | Same transaction, but all semantics in SQL | Same transaction; `BEGIN` still precedes the first read |
| Cycles and SCC fixed point (`04` §3.6) | Unchanged. The cache holds tuples, never node values, so memo, provisional values and passes are untouched. The proofs need reads to be a function of snapshot, revision and key, which still holds | Lost: `UNION` reachability is not stratified evaluation | Not involved |
| `max_depth` | Same check, same point: hints do not enter `eval` | No equivalent | Not involved |
| `max_check_fanout` | Same point. A cached forward answer is always complete: a speculative key over its row cap is not cached, and the evaluator reads it in full | No equivalent | Not involved |
| `max_check_reads` | Same point. It and `store_reads` count reads the evaluator asks for, hit or miss, so counts are identical. Physical work is bounded separately (below) | No equivalent | Not involved |
| Fail closed | A failed statement is `Err` (Postgres has aborted the transaction anyway). A row that will not parse makes a speculative key uncached, so the error surfaces only if evaluation needs that read, exactly as before | Would need rebuilding | A failure is the same `Err`; the transaction is rolled back |
| Trace | Same hooks, same order, independent of the tracer. Only `duration` moves: the node that misses absorbs the statement | None | Not involved |

New failure mode: a statement carrying speculative reads can fail where the lazy read would
have succeeded (for example under `statement_timeout`). That is an `Err`, so it fails closed,
but an error can appear on a check that would have answered. Caps below keep statements small.

## Bounds on speculation

- Round trips never increase: a statement is sent only for a read the evaluator asked for and
  would otherwise have sent alone. The demanded read has no row cap, so it needs no second
  statement.
- At most 1,024 reads per statement, and 64 rows per speculative key.
- Speculation ramps, from 32 reads per statement doubling to the cap, so a wide arrow decided
  by its first object does not pay for a full batch. A `lookup_resources` window starts at the
  cap, since it is likely to use what it fetches.
- Speculative reads per evaluator are limited to `1,024 + 16 × reads demanded`, so physical
  work stays linear in what `max_check_reads` already bounds. Past it, only demanded reads are
  sent.
- The cache is per evaluator and emptied past 16,384 answers. Emptying only costs a re-read.

## Scope

Postgres only. The new `ReadStore` methods are provided, and the default says the store does
not batch, so memory, SQLite and pysqlite keep their exact read paths: in-process point reads
have no round trip to save. `lookup_subjects` keeps its reads and gains only (c), since it
has no benchmark scenario and its own evaluator. `check_bulk` gains read-ahead per subject.
